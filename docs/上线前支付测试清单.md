> 前置：小程序已发布/在备案，云函数已部署，`createPayment` 与 `wechatPayNotify` 已按 `.secrets/README.md` 配置支付环境变量。

## 第 0 步 · 配置与代码自检（本机，不花钱）

- [ ] **0.1 密钥自检**（验证 `.secrets/wechat-pay.env` 里的 API v3 密钥可用、算法一致）
  ```bash
  node scripts/pay-notify-simulator.mjs self-check-encrypt --use-real-key
  ```
  预期输出：`AES-256-GCM 往返：✓ 通过`。若报「必须是 32 字节」，说明密钥填错（去商户平台账户中心 → API 安全核对）。

- [ ] **0.2 算法自检**（不依赖你的密钥，验证工具与云函数算法一致）
  ```bash
  node scripts/pay-notify-simulator.mjs self-check-encrypt
  ```
  预期：`✓ 通过`。

- [ ] **0.3 线上验签防线**（伪造回调打到线上回调地址，必须被拒）
  ```bash
  node scripts/pay-notify-simulator.mjs send-fake \
    --url https://cloudbase-d2gq023qn50e9d82f.service.tcloudbase.com/wechatPayNotify
  ```
  预期：`HTTP 401` + `签名错误` + `✓ 伪造回调被拒`。
  ⚠️ 若线上返回 200/成功，说明验签没生效，立即停用支付排查。

## 第 1 层 · 真机小额支付回归（最关键，建议用 0.01~1 元档测试商品）

> 规则：用**自己的微信号**在**真机**（非开发者工具模拟器）操作；每笔支付后立刻去**微信支付商户后台 → 交易账单**核对金额与单号。

### 商品订单（微信支付）
- [ ] **1.1 正常支付**：选商品 → 提交订单 → 微信支付 → 支付成功
  - 订单状态：`待支付 → 待自提/已付款/待发货`（`wechatPayNotify/index.js:798-856`）
  - 库存：锁定数 -1、已售 +1（后台商品库存核对）
  - 优惠券：下单锁券 → 支付核销
  - 积分/消费额：按规则累计
  - 微信「订单发货信息」：自提/堂饮支付成功自动上传（`wechatShipping.js`）
  - 商户后台：交易金额、商户单号与小程序订单一致
- [ ] **1.2 支付后立刻关掉页面再进**：订单详情显示已支付、按钮变为可退款/售后入口
- [ ] **1.3 取消支付**：发起支付但不付款，订单保持 `待支付`；15 分钟超时后自动变 `已取消`，库存/券释放（`releaseOrderLocks`）
- [ ] **1.4 超时后重新支付**：`lockedUntil` 过期后重新发起支付并成功 —— 重点回归 H1 竞态（`createPayment/index.js:1438-1451`），确认订单最终为已支付、库存只扣一次

### 茶室预约
- [ ] **1.5 预约 + 支付成功**：状态 `已确认`，到店/未到店流转正常
- [ ] **1.6 取消预约退款（全退）**：`payStatus → refunding → refunded`，微信原路退回
- [ ] **1.7 售后部分退款**：后台操作部分退，余额校验正确（`createPayment/index.js:320-513`）
- [ ] **1.8 重复点退款**：同一预约连续点两次退款，第二次提示「已退款」，不得重复退（回归 S2）

### 会员充值
- [ ] **1.9 真实充值**（若 `REAL_PAYMENT_ENABLED=true`）：充值套餐到账、积分入账、`memberCenter` 余额正确
- [ ] **1.10 模拟充值**（若未开真实支付）：`MEMBER_TEST_MODE` 白名单内可模拟充值并走余额下单

### 后台经营闭环
- [ ] **1.11 后台订单管理**：能看到新订单；取消订单、标记发货（快递）、人工收款流程可用
- [ ] **1.12 售后退款**：用户申请售后 → 后台审核 → 退款标记闭环（回归 M5：累计退款 ≤ 实付）
- [ ] **1.13 订阅消息**：支付成功触发授权，店员能收到新订单提醒（需后台配模板 ID）

## 第 2 层 · 异常与安全（第一次做最容易漏）

- [ ] **2.1 金额篡改**：抓包/改前端把订单金额改小提交 —— 服务端必须按落库金额收费，拒绝或按真实金额（`createOrder` 服务端算金额）
- [ ] **2.2 伪造回调**：用 0.3 的 `send-fake` 对线上发伪造报文 —— 必须 401 被拒
- [ ] **2.3 重复回调**：同一笔支付成功后，把真机收到的回调报文原样再发一次 —— 不得重复入账（幂等：`pending→confirming` 抢占 + ledger）
- [ ] **2.4 越权退款**：A 账号尝试对 B 的预约/订单退款 —— 必须被拒（回归 S1；修复前此场景可复现漏洞）
- [ ] **2.5 越权查单**：A 账号查 B 的订单/预约/充值记录 —— 必须空或报错（`_openid` 校验）
- [ ] **2.6 回调丢失模拟**：支付成功后不等回调，重启/等 5 分钟 —— 用 `reconcileRecharge`/查单补入账路径补齐（`createPayment/index.js:1152,1279`）
- [ ] **2.7 并发退款**：快速连续点两次退款/后台代退与用户取消同时发生 —— 不得超付（回归 S2）

- [ ] **3.2 异常订单巡检**：定期查 `payStatus` 为 `paid_exception / amount_mismatch / balance_error / refunding` 的订单，人工处理

本清单的第 1.4 / 1.8 / 2.3 / 2.4 / 2.7 项对应 `docs/支付安全审计报告.md` 里的 S1/S2/H1 等缺陷。**在修复这些缺陷之前做真机回归，只能暴露问题，不能覆盖风险**——建议先按审计报告修完 S1/S2/H1，再执行本清单。

## 工具说明

`scripts/pay-notify-simulator.mjs` 三个子命令（详见文件头部注释）：

| 命令 | 作用 | 对应清单 |
|---|---|---|
| `self-check-encrypt` | API v3 密钥与 AES-256-GCM 实现自检 | 0.1 / 0.2 |
| `build-payload` | 生成加密回调报文（结构对照） | 0.4 |
| `send-fake` | 伪造回调负向测试（验签防线） | 0.3 / 2.2 |

> 限制说明：工具无法生成「合法签名」的回调（签名需要微信平台私钥，仅微信侧持有），因此正向验签与真实入账只能用真机小额支付验证（第 1 层）。
