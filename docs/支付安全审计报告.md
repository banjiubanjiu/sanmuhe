# 支付安全审计报告（禾煦小程序）

- 审计日期：2026-08-10
- 审计范围：云函数 `createPayment`、`wechatPayNotify`、`createOrder`、`manageOperations`、`listMyRecords`、`memberCenter`，及定时器 `releaseOrderLocks`
- 审计方式：逐行代码审计，覆盖金额安全、回调验签/解密、幂等与并发、越权、注入、敏感信息、事务一致性

## 结论摘要

核心支付链路设计扎实：金额全部服务端计算、回调验签与 AES-256-GCM 解密完整、订单入账用 `payStatus pending→confirming` 条件更新原子抢占、用户侧查询带 `_openid` 归属校验、无代码注入、未发现打印私钥的日志。

**主要风险集中在「接口信任边界」与「并发原子性」**，按严重程度如下。建议优先修复 S1、S2、H1、H2 后，再做真机支付回归。

## 严重（必须修）

### S1 可伪造「管理员」标记，任意用户可替他人发起退款

- 位置：`createPayment/index.js:329-332`
- 现象：`refundReservation` 判断 `event.adminRefund === true || event.source === "manageOperations"` 即放行越权退款。`event` 完全由小程序前端伪造——任何用户 `wx.cloud.callFunction({ name: "createPayment", data: { action: "refundReservation", source: "manageOperations", adminRefund: true, ... } })` 就能对任意处于「已取消/已完成/异常待处理」且 `payStatus=refunding` 的预约发起退款、注入部分退款金额。
- 风险：越权操作他人资金（退款原路退回，无直接盗取，但可恶意退款他人预约、造成账务混乱），是典型的「云函数互调信任标记被前端伪造」漏洞。
- 修法（推荐）：`refundReservation` 只允许本人（`openid === row._openid`）退款；管理后台退款改由 `manageOperations` 内部独立入口（管理侧鉴权后再调用），不再接收外部 `event` 里的 `source/adminRefund` 标记。管理侧退款写审计日志并记录 reason。

### S2 退款发起无原子抢占，并发两次退款可累计超过实付（双退）

- 位置：`createPayment/index.js:347-391`（可退金额计算）与 `427-498`（发起微信退款 + 落库）
- 现象：退款前仅在内存中检查 `row.payStatus === "refunding"`，未用条件更新先抢占状态就调微信退款。两个并发请求读到相同 `alreadyRefundedFen`/`maxRefundFen`，各自生成不同 `out_refund_no` 各退一笔，累计超过实付。
- 风险：商家资金损失（超付退款）。
- 修法：退款前条件更新抢占，例如 `where({ _id, payStatus: "refunding", refundAmount: 当前已退 }).update({ payStatus: "refunding_pending" })`，`updated > 0` 才允许发起；落库以微信返回结果为准。

## 高（强烈建议修）

### H1 订单超时释放与支付回调竞态，可能误伤已支付订单并重复释放库存

- 位置：`createPayment/index.js:1438-1451`（isExpired 分支无条件更新为「已取消」+ 释放库存/券）与 `wechatPayNotify/index.js:819-843`（confirming 抢占 + confirmInventory）竞争
- 现象：用户在 `lockedUntil` 过期前后重新发起支付，`isExpired` 分支按旧状态直接释放库存；若回调已完成 `pending→confirming` 抢占并执行 `confirmInventory`，释放逻辑会再扣一次 `lockedStock`（可成负数），随后回调把订单覆盖回「已付款」。结果：订单已收款但库存账实不符。
- 修法：`isExpired` 分支同样用条件更新（`where({ _id, payStatus: "pending", status: "待支付" })`），`updated === 0` 则重新读库判断；释放库存/券只在抢占成功后执行。

### H2 回调处理中途失败/与用户取消竞态后，已支付订单缺少自动补账路径

- 位置：`wechatPayNotify/index.js:802-813`（非 pending 一律落 `paid_exception` 并 return，不补入账）+ `listMyRecords/index.js:418-460`（用户取消）
- 现象：① 抢占成功到写库之间抛异常（`confirmInventory` 网络失败等），订单停在 `confirming`，微信重试回调走 `paid_exception` 分支，永远不补入账；② 用户在 `confirming` 窗口取消成功后，回调随后把订单覆盖为「已付款」，用户以为已取消。
- 修法：`confirming` 状态的重试回调应继续完成剩余入账（而非标异常）；`paid_exception` 增加自动重新对账（查微信单补入账）；取消逻辑对 `confirming` 状态直接拒绝并提示「支付确认中」。

### H3 优惠券领取非原子，可并发重复领取/超发

- 位置：`memberCenter/index.js:831-887`（claimCoupon：count 判断 + `issued>=stock` 判断后，`issued: _.inc(1)` 与 `user_coupons.add` 独立写）
- 现象：两个并发请求同时通过检查，都 inc、都 add，突破 `claimLimit=1` 与 `stock` 上限。
- 修法：发放改为条件更新抢占（`where({ _id, issued: _.lt(stock) }).update({ issued: _.inc(1) })`，`updated > 0` 才 add 用户券）；同一用户限领用先占位后回填或唯一约束。
